# Troubleshooting the AWS SaaS source

From SailPoint's AWS SaaS and AWS connector troubleshooting pages and the developer forum.

| Symptom | Cause | Fix |
|---|---|---|
| Agentic Fabric → agent → **Capabilities** empty for an AgentCore agent (MCP Servers / Tools / Skills all 0) | Connector limitation (tested 2026-10): capabilities come from **Bedrock Agent action groups** (shown as Tools); AgentCore runtimes have no such field. Not filled by AgentCore Gateway targets, gateway tags/resource policies, runtime tags or env vars, or an OpenAPI schema on an inbound gateway target listing the tools | Nothing to configure. Use a Bedrock Agent with action groups if Tools must show, or raise it with SailPoint |
| SailPoint's own role (e.g. `SailPointISCRole…`) missing from IAM Role machine accounts; Identity Graph "only IAM role machine accounts are supported" on AgentCore accounts | By design (observed, not documented): the IAM Role dataset skips roles that trust SailPoint's `ciem_universal` principal and AWS-reserved IAM Identity Center roles (`/aws-reserved/sso…`). AgentCore workload identities (`mcpdemo-gw-*`, `<agent>-<id>`) are accounts but not IAM roles, so they have no graph | Nothing to fix. Review the connector role in AWS (`aws iam list-role-policies --role-name <role>`); open an IAM-role account (e.g. the agent's execution role) for the Identity Graph |
| Dataset aggregation: `Permission error (bedrock-agentcore): n/n accounts, n/n regions` (or `bedrock`) | Role lacks an action the connector calls — SailPoint's documented AgentCore policy misses gateway, resource-policy and tag reads | Find the denials: `aws cloudtrail lookup-events --region <r> --lookup-attributes AttributeKey=EventSource,AttributeValue=bedrock-agentcore.amazonaws.com` and filter `errorCode == AccessDenied` for your role; add them to the asset policy and rerun `aws-setup.sh --agentcore --apply`. Current `policy-bedrock-agentcore-discovery.json` already includes the known ones |
| Token: `invalid_client` / "Full authentication is required" | Wrong PAT, wrong tenant host, or Client ID and Secret swapped (ID = 32 hex, Secret = 64) | The script flags the swap; otherwise check `ISC_TENANT` and regenerate the PAT |
| Peek / account aggregation: `no schema provided for account list`; entitlement aggregation: `EntitlementList.getSchema()` is null | Source lacks `spConnectorSupportsCustomSchemas: true` (and the other UI defaults) — ISC doesn't send schemas to the connector | PATCH the defaults in (list in `references/isc-api.md`), wait a few minutes / retry — the instance caches config. Sources made by current `create` already have them |
| Test: `NullPointerException … ConnectorProxy.getInternalConnector()` | Source has no `spConnectorInstanceId` (created via API without `spConnectorSpecId`) | Delete the source and recreate it with `isc-source.sh create` (sends the spec id) |
| Test / UI Test Connection: `NullPointerException … "req.input" is null`; source "Not Responding" | AWS SaaS source never aggregated yet — test/health check fails until the first aggregation, regardless of config | `peek` (reads a few IAM users); if that works, run `aggregate`, then `test` → `SUCCESS`, source becomes HEALTHY |
| `check-connection`: `Value of 'cluster' cannot be null` | Source has no connector instance (see first row) | Same fix |
| `aws-setup.sh` stops: role already exists | Another SailPoint tenant/CIEM uses that role name (check CloudTrail: who assumes it) | Use a different `--role-name`; never rewrite a trust policy that's in use |
| Test connection: **"AWS Client creation failed"** | Role missing in the management account; or an ARN entered instead of the role name; or wrong Management Account ID (forum: malformed `arn:aws:iam::aws:role/...`) | `configure --role-name <name>` (no ARN); confirm the role exists in the management account; check `--mgmt-account-id` |
| `AccessDenied` on `sts:AssumeRole` | External ID mismatch, trust principal wrong for the partition, or role not deployed in that account yet | Compare the External ID on the source with the role's trust policy; GovCloud uses 229634586956; check StackSet instances: `aws cloudformation list-stack-instances --stack-set-name SailPoint-ISC-AWS` |
| STS AccessDenied while listing accounts | Role absent or differently named in some member accounts | StackSet instance status per account; new OUs need `--targets` to include them |
| `AWSOrganizationsNotInUseException` | Account not in an Organization | Enable Organizations (all features) |
| Organizations `AccessDenied` | Role in management account lacks SPOrganizationPolicy, or Management Account ID points at a member | Redeploy the management stack; fix Management Account ID |
| `InvalidConfigurationException` about Management Account ID | Manage All Accounts / included accounts set without Management Account ID | `configure` always sets it; check the key map maps `managementAccountId` |
| IAM role dataset scans 0 objects | Missing `iam:GetAccountAuthorizationDetails` | Included in `policy-aggregation.json`; redeploy if an older role is in use |
| Throttling errors during aggregation | AWS API rate limits | Raise retry/backoff settings on the source; lower Page Size |
| Aggregation timeout | Large org | Raise `aggregateTimeout` (e.g. 1800; max 3600) via `PATCH /connectorAttributes/aggregateTimeout` |
| Unwanted work items when revoking policies via certification | `NO_PERMISSIONS_PROVISIONING` / `NO_GROUP_PERMISSIONS_PROVISIONING` feature | Remove it from the source `features` |
| Provisioning error: group from another account | Access profile groups in a different account than the user being created | Keep access-profile entitlements in the user's account |

Not supported by this connector: IAM Identity Center users/permission sets (separate CIEM AWS connector; you can't
enable CIEM on AWS SaaS for a management account already using the CIEM connector). VA → SaaS migration is one-way.
