# AWS permissions for the ISC "Amazon Web Services SaaS" connector

Source: SailPoint docs, `documentation.sailpoint.com/connectors/saas/aws/help/saas_connectivity/aws/`
(required_permission, mgo_source_policies, non_mgo_policies, manual_configuration, machine_identity_governance_policies).

## How SailPoint reaches AWS

SailPoint's own role assumes a role **you** create:
1. the role in the **management account** lists the organization's accounts and org objects (OUs, SCPs);
2. a role with the **same name and same External ID** in each member account reads that account's IAM data.

Role names must match across accounts, and the External ID is generated by ISC (read-only on the source's
Connection Settings page). A standalone account without AWS Organizations is not supported — enable Organizations
(`aws organizations create-organization --feature-set ALL`) and it becomes its own management account.

## Trust policy

Principal by partition:
- Commercial: `arn:aws:iam::874540850173:role/ciem_universal`
- GovCloud: `arn:aws-us-gov:iam::229634586956:role/ciem_universal`

Template: `assets/trust-policy.json.tmpl` (`sts:AssumeRole` + `sts:ExternalId` condition). If Activity Insights is
licensed, the action must be `["sts:AssumeRole", "sts:TagSession"]` — not done by `aws-setup.sh`; add it by hand.

## Permission policies (assets/)

| File | Inline name | Where | Why |
|---|---|---|---|
| `policy-aggregation.json` | SPAggregationPolicy | every account | read IAM users, groups, roles, policies, credentials metadata, tags. Includes `iam:GetAccountAuthorizationDetails`, which troubleshooting says the IAM role dataset needs (otherwise it scans 0 objects) |
| `policy-organization-mgo.json` | SPOrganizationPolicy | management account | read accounts, OUs, SCPs (multiple-group-object source). Non-MGO setups only need `organizations:ListAccounts` |
| `policy-provisioning-mgo.json` | SPProvisioningPolicy | every account, only with `--provisioning` | create/delete users, keys, login profiles; group membership; attach/detach policies |
| `policy-bedrock-agent-discovery.json` | SPBedrockAgentDiscoveryPolicy | every account, only with `--bedrock` | discover Bedrock Agents (+ aliases, versions, action groups, knowledge bases, data sources, collaborators); `kms:Decrypt`/`GenerateDataKey` for CMK-encrypted agents |
| `policy-bedrock-agentcore-discovery.json` | SPBedrockAgentCoreDiscoveryPolicy | every account, only with `--agentcore` | discover AgentCore runtimes, endpoints, versions, workload identities, credential providers, gateways (+ targets), resource policies, tags. SailPoint's documented policy lacks `ListGateways`, `GetResourcePolicy`, `ListTagsForResource` (and the gateway reads that follow) — the connector calls them and the dataset fails with "Permission error (bedrock-agentcore)" without them (seen in CloudTrail, 2026-10) |

The JSON in SailPoint's docs has syntax errors (missing `{`, trailing commas) and the published CloudFormation
templates render some `Resource` values as `""`. The files here are corrected; `aws-setup.sh --print-template` shows
the CloudFormation the script deploys.

## Optional add-ons (not deployed by the script)

- **Activity Insights:** `AWSCloudTrail_ReadOnlyAccess`-style policy — `cloudtrail:Get*`, `Describe*`, `List*`,
  `LookupEvents` — plus `sts:TagSession` in the trust policy. Commercial only.
- **CIEM:** CloudTrail bucket read (`s3:GetBucketLocation`, `s3:ListBucket` on the bucket, `s3:GetObject` on objects).
- **Other machine identity discovery:** Amazon Connect, Amazon Quick, IAM credentials, Secrets Manager — see
  `machine_identity_governance_policies` in the docs for the exact action lists. (Bedrock and AgentCore are
  deployed by the script; see the table above.)

## Manual setup (no CloudFormation)

In each account: IAM → Roles → Create role → Custom trust policy (template above, External ID filled in) → attach
the policies above → same role name everywhere. Verify on the role's Trust relationships tab that the principal
account is 874540850173 (commercial) or 229634586956 (GovCloud).
